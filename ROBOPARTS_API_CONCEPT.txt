ROBOPARTS.ai API AND KNOWLEDGE GRAPH

Version: 0.2.0
Status: Implementation specification
Purpose: Define implementable application interfaces, data contracts, validation rules, persistence requirements, and traceability behavior for the ROBOPARTS.ai robotics component marketplace.

1. PURPOSE AND IMPLEMENTATION PRINCIPLES

ROBOPARTS.ai provides structured discovery, supplier information, robot configuration, compatibility assessment, component traceability, and requests for quotation (RFQs).

This specification distinguishes between:

API contract: The required interface and behavior.
Implementation: The server code, database, authentication, and integrations that make the interface operational.
Verification: Tests demonstrating that the implementation meets the contract.

An endpoint described in this document is not considered operational until it has been implemented, deployed, and tested.

2. API CONVENTIONS
Base path: /api/v1
Data format: JSON using UTF-8 encoding.
HTTP methods: GET for retrieval and POST for creation.
All timestamps: ISO 8601 UTC.
Identifiers: Stable, unique identifiers generated or validated by the server.
Validation failures: HTTP 400 or 422, according to the implementation's documented convention.
Missing resources: HTTP 404.
Unauthenticated requests: HTTP 401.
Unauthorized requests: HTTP 403.
Rate-limited requests: HTTP 429.
Unexpected server failures: HTTP 500, without exposing secrets or internal stack traces.

All endpoints must define their authentication, authorization, validation, and persistence requirements.

3. PRODUCT ENDPOINTS
GET /api/v1/products — List and filter products.
POST /api/v1/products — Register a product.
GET /api/v1/products/{product_id} — Retrieve product details.

Product records should support manufacturer, model, part number, component class, specifications, declared capabilities, and evidence references.

4. ORGANIZATION ENDPOINTS
GET /api/v1/organizations — Search authorized organization records.
POST /api/v1/organizations — Register an organization.
GET /api/v1/organizations/{organization_id} — Retrieve an organization record.

Organization records may represent manufacturers, distributors, suppliers, integrators, and other authorized participants.

5. ROBOT AND CONFIGURATION ENDPOINTS
GET /api/v1/robots — List robots.
POST /api/v1/robots — Register a robot.
GET /api/v1/robots/{robot_id}/bom — Retrieve a bill of materials.
POST /api/v1/bom-items — Associate a component with a robot configuration.

Every BOM association must identify the relevant component, configuration, quantity, and applicable version. Configuration changes must preserve required historical records.

6. COMPATIBILITY ENDPOINTS
POST /api/v1/compatibility-assessments — Create a compatibility assessment.
GET /api/v1/compatibility-assessments/{assessment_id} — Retrieve assessment results.

Assessments must reference specific component and robot configuration versions, record their supporting evidence, and distinguish verified facts from estimates and AI-generated recommendations.

Compatibility assessments are not physical safety certification.

7. TRACEABILITY ENDPOINTS
POST /api/v1/events — Record a component lifecycle event.
GET /api/v1/instances/{instance_id}/traceability — Retrieve authorized component identity, BOM relationships, provenance, and lifecycle events.

Lifecycle records must preserve relevant history. Corrections should be recorded through auditable amendments rather than silently overwriting historical events.

8. KNOWLEDGE GRAPH ENDPOINTS
GET /api/v1/ontology/relationships — Query authorized ontology relationships.
POST /api/v1/ontology/relationships — Create a validated relationship.

Every relationship must specify its meaning, source entity, target entity, provenance, and validation status.

The API must verify that source and target entity types are compatible with the relationship definition. AI-generated relationships remain proposed until approved through the applicable review process.

9. MARKETPLACE AND RFQ ENDPOINTS
9.1 Required endpoints
POST /api/v1/rfqs — Create an RFQ.
GET /api/v1/rfqs/{rfq_id} — Retrieve an authorized RFQ.
GET /api/v1/rfqs/{rfq_id}/quotes — Retrieve quotations the requesting user is authorized to access.
POST /api/v1/supplier-listings — Create a supplier listing.
9.2 RFQ submission contract

The RFQ creation endpoint must accept a JSON request containing:

product_id — Product identifier when requesting a specific product; otherwise optional for general sourcing requests.
part_number — Requested manufacturer or supplier part number, if known.
quantity — Requested quantity, when applicable.
company_name — Requesting company.
contact_name — Contact person's name.
contact_email — Valid contact email address.
requirements — Description of the request, specifications, and intended application.
robot_configuration_id — Optional configuration reference.
source — Optional marketplace source or campaign reference.

The server must validate required fields, enforce input size limits, verify referenced records when supplied, and apply appropriate abuse-prevention controls.

The server must not trust client-supplied ownership, authorization, approval status, or supplier permissions.

9.3 Successful submission

A successfully created RFQ must be persisted before the server reports success.

The server should return HTTP 201 Created and a response containing:

rfq_id — Unique RFQ identifier.
status — Initial workflow status, such as submitted.
created_at — Creation timestamp.
message — Human-readable confirmation.
