1. PURPOSE

This document defines the initial proposed software architecture for the RoboParts.ai API and database prototype.

The objective is to establish a foundation for:

Component registration.
Manufacturer and product records.
Product-family classification.
Serialized component identity.
Robot registration.
Robot configurations.
Bills of materials.
Component-to-robot relationships.
Compatibility records.
Capability records.
Maintenance history.
Fault history.
Recall identification.
Lifecycle traceability.

The initial implementation should prioritize a lightweight, understandable architecture that can be tested locally and expanded later.

2. IMPLEMENTATION STATUS

IMPORTANT:

The implementation described in this document is a proposed starting point.

The code examples and architecture have not been represented as tested, production-ready, or deployed software.

All implementation steps require execution, testing, validation, and revision.

7. INITIAL DATABASE SCHEMA

The following is a conceptual SQL starting point.

sql
CREATE TABLE manufacturers (
    manufacturer_id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    website TEXT,
    country TEXT,
    created_at TEXT
);

CREATE TABLE product_families (
    family_id TEXT PRIMARY KEY,
    family_name TEXT NOT NULL,
    component_class TEXT NOT NULL,
    description TEXT,
    taxonomy_version TEXT
);

CREATE TABLE products (
    product_id TEXT PRIMARY KEY,
    manufacturer_id TEXT NOT NULL,
    family_id TEXT,
    manufacturer_part_number TEXT NOT NULL,
    model TEXT,
    architecture_type TEXT,
    product_status TEXT,
    FOREIGN KEY (manufacturer_id)
        REFERENCES manufacturers(manufacturer_id),
    FOREIGN KEY (family_id)
        REFERENCES product_families(family_id)
);

CREATE TABLE components (
    component_id TEXT PRIMARY KEY,
    product_id TEXT,
    manufacturer_serial_number TEXT,
    product_revision TEXT,
    manufacturing_lot TEXT,
    manufacturing_date TEXT,
    lifecycle_status TEXT,
    verification_status TEXT,
    created_at TEXT,
    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);

CREATE TABLE robots (
    robot_id TEXT PRIMARY KEY,
    robot_name TEXT NOT NULL,
    robot_class TEXT,
    platform_model TEXT,
    deployment_status TEXT,
    created_at TEXT
);

CREATE TABLE configurations (
    configuration_id TEXT PRIMARY KEY,
    robot_id TEXT NOT NULL,
    configuration_revision TEXT,
    effective_date TEXT,
    configuration_status TEXT,
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id)
);

CREATE TABLE subsystems (
    subsystem_id TEXT PRIMARY KEY,
    robot_id TEXT NOT NULL,
    parent_subsystem_id TEXT,
    subsystem_name TEXT NOT NULL,
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id),
    FOREIGN KEY (parent_subsystem_id)
        REFERENCES subsystems(subsystem_id)
);

CREATE TABLE component_installations (
    installation_id TEXT PRIMARY KEY,
    component_id TEXT NOT NULL,
    robot_id TEXT NOT NULL,
    subsystem_id TEXT,
    installation_date TEXT,
    removal_date TEXT,
    installation_status TEXT,
    FOREIGN KEY (component_id)
        REFERENCES components(component_id),
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id),
    FOREIGN KEY (subsystem_id)
        REFERENCES subsystems(subsystem_id)
);

CREATE TABLE bills_of_materials (
    bom_id TEXT PRIMARY KEY,
    robot_id TEXT NOT NULL,
    configuration_id TEXT,
    bom_revision TEXT,
    bom_status TEXT,
    created_at TEXT,
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id),
    FOREIGN KEY (configuration_id)
        REFERENCES configurations(configuration_id)
);

CREATE TABLE bom_lines (
    bom_line_id TEXT PRIMARY KEY,
    bom_id TEXT NOT NULL,
    component_id TEXT,
    product_id TEXT,
    quantity INTEGER NOT NULL,
    installation_location TEXT,
    required_or_optional TEXT,
    FOREIGN KEY (bom_id)
        REFERENCES bills_of_materials(bom_id),
    FOREIGN KEY (component_id)
        REFERENCES components(component_id),
    FOREIGN KEY (product_id)
        REFERENCES products(product_id)
);

CREATE TABLE lifecycle_events (
    event_id TEXT PRIMARY KEY,
    component_id TEXT NOT NULL,
    robot_id TEXT,
    event_type TEXT NOT NULL,
    event_date TEXT,
    description TEXT,
    evidence_reference TEXT,
    FOREIGN KEY (component_id)
        REFERENCES components(component_id),
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id)
);

CREATE TABLE maintenance_events (
    maintenance_id TEXT PRIMARY KEY,
    component_id TEXT NOT NULL,
    robot_id TEXT,
    maintenance_type TEXT,
    service_date TEXT,
    description TEXT,
    status TEXT,
    FOREIGN KEY (component_id)
        REFERENCES components(component_id),
    FOREIGN KEY (robot_id)
        REFERENCES robots(robot_id)
);

CREATE TABLE fault_events (
    fault_id TEXT PRIMARY KEY,
    component_id TEXT,
    robot_id TEXT,
    fault_code TEXT,
    severity TEXT,
    event_timestamp TEXT,
    description TEXT
);

CREATE TABLE recalls (
    recall_id TEXT PRIMARY KEY,
    manufacturer_id TEXT,
    product_id TEXT,
    recall_reference TEXT,
    affected_lot TEXT,
    affected_revision TEXT,
    required_action TEXT,
    recall_status TEXT
);


This schema is a starting point only.

Before implementation, the database design must be reviewed for constraints, indexing, historical assignment handling, versioning, and data validation.

8. DATABASE DESIGN REQUIREMENTS

The database should support:

Unique identifiers.
Foreign-key relationships.
Explicit measurement units.
Timestamped events.
Versioned configurations.
Versioned BOMs.
Historical component assignments.
Manufacturer and supplier references.
Source and evidence references.
Verification states.
Lifecycle states.

SQLite foreign-key enforcement must be explicitly enabled on database connections.

Historical installation records must be preserved.

A replacement should create a new installation event rather than overwriting the identity of the previously installed component.

12. API DATA VALIDATION

The API should validate:

Required identifiers.
Manufacturer references.
Product references.
Component identity.
Measurement units.
Lifecycle transitions.
BOM relationships.
Compatibility status.
Timestamp formats.
Duplicate registrations.

17. KNOWN LIMITATIONS

The initial SQLite prototype is not intended to provide:

Production-grade multi-user operation.
Certified functional safety.
Real-time robot control.
Guaranteed recall notifications.
Manufacturer data verification.
Automatic physical component discovery.
Validated predictive maintenance.
Autonomous safety enforcement.

These require separate implementation and validation.
